# AI Workflow Documentation

This document describes the architectural approach, tooling, and LLM orchestration logic used to build this AI-Powered Workflow Automation System.

## Architectural Approach
The system was designed as a full-stack, containerized monorepo consisting of:
- **Backend**: FastAPI (Python) orchestrating the background task queue and data validation.
- **Frontend**: Next.js 14, Tailwind CSS, Shadcn/UI (hand-coded for stability), and Tremor for analytics.
- **Database / Storage**: Supabase handles binary document storage and relational SQL data logic.
- **Agent Orchestrator**: The system was built with "Antigravity," a Deepmind-designed Advanced Agentic Coding assistant. The agent orchestrated terminal commands, code generation, and iterative bug fixing to ensure a perfect local deployment.

## LLM Integration & SDK Pivot
**Model Used:** Gemini 2.5 Flash
We utilized the cutting-edge multimodal model from Google (via the `google-genai` SDK). The architecture was deliberately designed to pass raw binary byte streams straight from Supabase Storage into the Gemini context window via `types.Part.from_bytes()`. This eliminates the need for expensive intermediate file operations on the backend container.

## Multi-Record Extraction (Advanced Gold Star Feature)
When processing highly dense manufacturing logs containing multiple distinct operations, Gemini is instructed to return a JSON array containing multiple records:
```text
Return ONLY a valid JSON array of objects (even if there is only one record).
```
The FastAPI backend (`processor.py`) dynamically reads this output. If Gemini delivers a list of extractions, the background worker:
1. Validates and cleans `quantity_produced` (safe integer parsing/casting) for each entry.
2. Intercepts and maps Roman numeral shifts (`I, II, III`) to standard string digits (`1, 2, 3`).
3. Iteratively inserts each extraction as an independent record in the `extracted_records` table, all linked to the exact same parent `document_id`.

This enables dense document grouping in the UI history, displaying subsequent operations visually nested under a clean `↳` arrow.

## Intelligent Repair (Self-Healing Loop)
The backend orchestrator is built with a self-healing loop. If Gemini 2.5 Flash outputs invalid JSON (e.g., due to markdown formatting or hallucinated text outside the JSON block), the SDK `json.loads` parsing fails. The backend catches this `JSONDecodeError` and dynamically triggers a second "repair" prompt. This prompt explicitly passes the specific parse error back to the LLM:
`WARNING: The previous output was invalid JSON. Fix this error: {repair_prompt}`
This allows Gemini to self-correct its syntax in real-time before throwing a hard failure.

To further protect against Gemini arbitrarily wrapping JSON in Markdown code blocks (a common LLM quirk), the Python parsing engine explicitly strips ` ```json ` markers before loading.

## Analytics & Persistence
- **Ghost Uploads**: To prevent silent failures during asynchronous extraction, the API uses a robust SQL `LEFT JOIN` via Supabase to join the `documents` table to the `extracted_records`. This allows the UI to show files as "Processing" or "Failed", rather than disappearing entirely.
- **Empty States**: The Analytics engine uses mathematical aggregation safeguards to prevent dividing by zero or attempting to render UI charts (Tremor) before any completed JSON has been generated by the LLM.
